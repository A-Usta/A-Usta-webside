# M7.6 TEST Auth bootstrap

The script at `backend/a-usta56/tools/test-auth-bootstrap.mjs` creates three new, randomly named Auth users through Supabase's server-side Auth Admin API. It never edits an existing user. On a partial failure, it attempts to delete only user IDs returned by successful create calls in that same invocation.

## Safety boundary

- The target URL is fixed to `https://xnhxneziasqthkhhntkv.supabase.co`; any other value, including production, is rejected before a client is constructed.
- The service key is read only from `AUSTA_TEST_SUPABASE_SERVICE_ROLE_KEY` in the trusted process environment. The script requires a JWT with the TEST project ref and `service_role` claim. Do not pass it as a command-line argument, put it in a file in the repository, or put it in output.
- The script calls `supabase.auth.admin.createUser()` from `@supabase/supabase-js`; this API must only run in a trusted server environment. No public endpoint is added.
- The third account is labeled `provider_candidate`. The script sets no `app_metadata`, role claim, seller profile, or eligibility state. Provider actions remain unavailable unless the normal TEST business onboarding/approval flow produces a seller profile with `status='active'` and `verification_status='verified'`.
- Passwords are held in memory during creation and then written to a newly created OS temporary directory with owner-only permissions. Access tokens and service keys are not stored. The script prints only the private file path and a safe completion message; remove the temp file after controlled E2E work.
- The generated `example.invalid` addresses are not deliverable mailboxes. Email confirmation is set by the Admin API for TEST login.

## Run in a trusted TEST server environment

Provide these variables to the local process using the approved secret manager or protected environment injection. Do not retrieve a key from Render or Supabase Dashboard through an unapproved channel.

```sh
AUSTA_TEST_SUPABASE_URL=https://xnhxneziasqthkhhntkv.supabase.co
AUSTA_TEST_SUPABASE_SERVICE_ROLE_KEY=<inject from trusted TEST secret store>
```

Then, from `backend/a-usta56`:

```sh
node --test --test-reporter=tap tools/test-auth-bootstrap.test.mjs
node tools/test-auth-bootstrap.mjs
```

The unit tests use a synthetic JWT and a mocked Auth Admin client; they do not access Supabase, create accounts, or need any secret. The CI step runs only these offline tests.

The current Work environment has no approved server-side access to the protected TEST Auth Admin key. Therefore no accounts, sessions, or E2E data were created in this run. Authenticated E2E remains blocked until a human runs the bootstrap from the trusted TEST environment and makes the generated temporary credential file available to the isolated E2E runner without copying it to GitHub.
